- # 线程上下文切换
  
	- ## 上下文切换的安全问题
	
		- 当有多个线程同时对一个变量进行操作时，可能出现下面这种问题：线程1 计算变量 a+1 的值再将值赋给 a，线程2 计算变量 a-1 的值再将值赋给 a，当线程1 计算完结果后，cpu 时间片耗尽，未能给 a 赋值，然后线程2 计算并赋值了 a-1，再将控制权转移给线程1，这时线程1 再对变量 a 进行赋值，a 此时的值就是 a+1，而不是 a。
	
	- ## 临界区
	
		- 一段代码内如果存在对共享资源的多线程读写操作，称这段代码为临界区
	
	- ## 竞态条件
	  
		- 多个线程在临界区内执行，由于代码的执行序列不同导致结果无法预测，称之发生了竞态条件


- # synchronized 对象锁
  
	- 为了避免临界区的竞态条件发生，有阻塞式和非阻塞式的两种解决方式，这里使用阻塞式的 对象锁 
	  
	- 对象锁使同一时刻至多只有一个线程能持有对象锁，其他线程想获得这个对象锁时会被阻塞住，这样就能保证拥有锁的线程可以安全的执行临界区内的代码，不用担心线程的上下文切换
	  
	- 虽然 Java 中互斥和同步都使用 `synchronized` 关键字完成，但它们有所区别：
	  
		- 互斥是保证临界区的竞态条件发生，同一时刻只能有一个线程执行代码
		  
		- 同步是因为线程执行的先后，顺序不同，需要一个线程等待其他线程运行到某个点
	
	- `synchronized` 示例：
	  ```java
		  static finla Object lock = new Object(); // 作为锁的对象，由所有线程共享
		  static int counter = 1; // 在临界区处理的共享变量
		  Thread t1 = new Thread(() -> {
			  for (int i = 0; i < 100; i++) {
			  synchronized(lock) {
				  counter++;
				  }
			  }
		  })
		  
		  Thread t2 = new Thread(() -> {
			  for (int i = 0; i < 100; i++) {
			  synchronized(lock) {
				  counter--;
				  }
			  }
		  })
	  ```
	
	- `synchronized` 实际是用对象锁保证了临界区内代码的原子性，临界区内的代码对外是不可分割的，不会被线程切换打断
	
	- 如果将 `synchronized` 放到 for 循环外，那么对象锁保护的就是这一百次循环的所有代码，等到这些代码都执行完后才会解除锁
	  
	- 如果 t1 和 t2 使用的是不同的锁对象，这种情况就相当于没有上锁
	  
	- 如果 t1 加锁，t2 不加锁，那么 t2 就不会有尝试获取对象锁的行为，会直接执行临界区代码，也和都没上锁相同
	  
	- ## synchronized 加在方法上
	  
		- ### 加在普通方法上
		  ```java
		  class Test1 {
			  public synchronized void test() {}
		  }
		  // 上面等价于
		  class Test1{
			  public void test(){
				  synchronized(this){}
			  }
		  }
		  // 直接加在普通方法上相当于锁住了 this 对象，即当前方法
		  ```
	
		- ### 加在静态方法上
		```java
		class Test2 {
			public static synchronized void test(){}
		}
		
		// 等价于
		
		class Test2 {
			public static void test() {
				synchronized(Test2.class) {}
			}
		}
		
		// 直接加在静态方法上相当于锁住了类对象
		```


- # 变量的线程安全分析
  
	- ## 成员变量与静态变量
	  
		- 如果它们没有共享（public），则线程安全
		  
		- 如果它们是共享的，那么分两种情况
		  
			- 如果只有读操作，则线程安全
			  
			- 如果有读写操作，那么需要考虑线程安全
	  
	- ## 局部变量
	  
		- 局部变量是线程安全的，局部变量是指在方法内创建的变量，不在方法间共享
		  
		- 但局部变量引用的对象未必线程安全，局部变量引用的对象指局部变量指向的堆中的对象实体。
		  
			- 如果该对象没有逃离方法的作用范围，则线程安全
			  
			- 如果该对象逃离方法的作用范围，需要考虑线程安全
	
	- `String, Integer StringBuffer` 等方法都是线程安全的，这里的线程安全是指，多个线程调用它们同一个实例的方法时，是线程安全的，可以理解为：它们的每个方法是原子的，但它们组合起来不是线程安全的
	  
	- `String, Integer` 是不可变类，是线程安全的，对 String 操作的方法是在原本 String 的基础上返回一个新的 String


- # Monitor
  
	- Monitor 被翻译为监视器或管程
	  
	- 每个 Java 对象都可以关联一个 Monitor 对象，如果使用 synchronized 给对象上锁后，该对象头的 Mark Word 中就被设置了执行 Monitor 对象的指针


- # 其他锁
  
	- 每次都使用 Monitor 锁都太过麻烦，Java 提供了其他类型的锁
	
	- ## 轻量级锁
	  
		- 使用场景：如果一个对象虽然有多线程访问但多线程访问的时间是错开的，不会竞争使用，那么就可以使用轻量级锁来优化
		  
		- 轻量级锁对使用者是透明的，即语法仍然是 `synchronized`
		  
		- ### 锁膨胀
		  
			- 如果在尝试加上轻量级锁时无法成功，当情况为已经有对象为其加上了轻量级锁时，就会进行锁膨胀，使锁从轻量级锁膨胀为重量级锁 Monitor
	
	- ## 自旋优化
	  
		- **自旋重试**是一种并发优化策略：线程不立刻挂起自己，而是在一个循环中反复检查某个条件（如锁是否已被释放、CAS 是否成功），直到条件满足为止。整个过程线程一直处于 **Runnable** 状态，就像在“原地打转”，因此得名“自旋”。
		
		- 重量级锁竞争时，可以使用自旋来优化，如果当前线程自旋成功（即这时候锁线程已经退出了同步块，释放了锁），这时当前线程就可以避免阻塞
	
	- ## 锁重入
	  
		- **锁重入**指的是：**同一个线程**在外层方法中已经获取了某个锁，当它再次请求**同一个锁**时，可以直接进入临界区，而不会被自己阻塞，同时锁的持有计数会递增。
	
	- ## 偏向锁
	  
		- **偏向锁**是 JVM 为优化**单线程重复获取同一锁**场景而引入的一种锁状态。它的核心思想是：**锁会“偏袒”第一个获得它的线程**，之后如果同一个线程再次进入同步块，无需任何 CAS 或同步操作，直接进入。
		
		- ### 撤销
		  
			- 当其他对象使用偏向锁对象时，会将偏向锁升级为轻量锁
		
		- ### 批量重偏向
		  
			- 如果对象被多个线程访问，但没有竞争，此时就会将原本线程的偏向锁撤销，将其升级为轻量级锁
			  
			- 当这个类的偏向锁撤销总次数到达阈值（20次），JVM 会触发批量重定向，对于此类中尚未发生过撤销的其他对象，允许它们直接偏向到新的线程，不再重复撤销和升级的过程
		
		- ### 批量撤销
		 
			- 当撤销偏向1锁超过阈值（40次）后，JVM 会将整个类的所有对象变为不可偏向的，之后新建的对象也是不可偏向的
	
	- ## 锁消除
	  
		- 对于不可能被共享的对象加锁时，编译器会在编译时自动将锁消除以提高性能


- # wait-notify
  
	- 线程在执行时发现继续执行所需要的条件未被满足，就会调用 wait 方法，进入WAITING状态，不占用 cpu 时间片，此时其他线程可以使用 cpu 进行工作
	  
	- BLOCKED 和 WAITING 状态都属于阻塞状态，BLOCKED 状态的线程会在锁被释放时被唤醒，WAITING 状态会在条件就绪后被 notify 或 notifyAll 唤醒，此时不会立刻得到 cpu 的使用权，而是与其他线程竞争使用权
	  
	- ## wait
	
		- 使线程进入 WAITING 状态
		  
		- 可以带参使用，参数是 int 类型，单位是毫秒，当到达等待时间时还没有被唤醒，则继续向下执行不再等待
		
		- 使用示例：
		```java
			// lock 为锁对象
			synchronized(lock){
				try{
					lock.wait();
				}
				catch(略){};
			}
		```
	  
	
	- ## notify
	  
		- 随机唤醒一个处于 WAITING 状态的线程，当有多个线程处于 WAITING 状态时，可能会出现错误唤醒的情况，即达到了线程1 的条件，想要唤醒线程1 但却唤醒了线程2
		  
		- 可以为线程加一个 while 循环，结束条件为条件达到，然后唤醒使用 notifyAll,这样，即使错误唤醒，但由于 while 循环结束条件未满足，因此线程依然会处于 WAITING 状态
		  
		- 使用示例：
		```java
			// 单开一个线程后执行了 wait 方法
			synchronized(lock){
				try{
					lock.wait();
				}
				catch(略){};
			}
			
			// 在主线程中调用 notify 方法唤醒一个线程，或使用 notifyAll 唤醒所有线程
			synchronized (lock){
				lock.notify();
				// lock.notifyAll();
			}
		```
	
	- ## notifyAll
	  
		- 唤醒所有处于 WAITING 状态的线程
	
	- ## wait 和 sleep 的区别
	  
		- sleep 是 Thread 的静态方法，wait 是属于 Object 的方法，任何对象都有
		  
		- sleep 不需要配合 synchronized 使用，但 wait 方法需要
		  
		- sleep 在睡眠时不会释放对象锁，但 wait 方法会释放


- # Park Unpark
  
	- 用于暂停/恢复当前线程
	  
	- 调用方式：`LockSupport.park()/LockSupport.unpark()`
	  
	- 如果先调用 unpark 再调用 park，那么线程不会暂停
	  
	- ## 与 wait & notify 比较
	  
		- wait 必须先获得锁才能使用，park 不用
		  
		- park 是以线程为单位进行阻塞和唤醒（可以理解为是一对一的），而 wait 是随机进行唤醒
		  
		- park 可以先指向 unpark 方法，wait 不能先指向 notify 方法


- # 线程状态转换
  
	- ## NEW 可以单向转换为 Runnable
	  
		- 调用 `Thread.start()` 方法
	
	- ## Runnable 与 WAITING 可以相互转换
	  
		- 线程使用 synchronized 获取对象锁 lock 后
		  
			- 调用 `lock.wait()` 后线程由 Runnable 转为 WAITING
			  
			- 调用 `lock.notify(), lock.notifyAll(), Thread.interrupt()` 后
			  
				- 竞争锁成功，线程由 WAITING 转为 Runnable
				  
				- 竞争锁失败，线程由 WAITING 转为 BLOCKED
		
		- 当线程调用`Thread.join()` 方法时，线程从RUNNABLE 转为 WAITING
		  
		- 当线程调用 `LockSupport.park()` 时，线程从RUNNABLE 转为 WAITING
		
		- 当线程调用 `LockSupport.unpark()/Thread.interrupt()` 时，线程从 WAITING 转为 RUNNABLE
	
	- ## RUNNABLE 可以和 TIMED_WAITING 相互转换
	  
		- 线程使用 synchronized 获取对象锁 lock 后
		  
			- 调用`lock.wait(Long n)`后，线程从 RUNNABLE 转换为 TIMED_WAITING
			  
			- 等待超过 n 毫秒，或调用 `lock.notify(), lock.notifyAll(), Thread.interrupt()` 后
			  
				- 竞争锁成功，线程由 WAITING 转为 Runnable
				  
				- 竞争锁失败，线程由 WAITING 转为 BLOCKED
		
		- 调用`Thread.join(Long n) / Thread.sleep(Long n)` 时，线程从 RUNNABLE 转为 TIMED_WAITING，join 的Thread 指的是线程变量名，sleep 的 Thread 就是 Thread
		  
		- `Thread.sleep(Long n)` 等待超过 n 毫秒后，线程由 TIMED_WAITING 转为 RUNNABLE
		  
		- `Thread.join(Long n)` 等待超过 n 毫秒 或 线程运行结束，或调用了当前线程的`interrupt()`时，当前线程由 TIMED_WAITING 转为 RUNNABLE
	
	- ## RUNNABLE 与 BLOCKED 可以相互转换
	  
		- 线程使用 synchronized 获取了对象锁时，如果竞争失败，线程会从 RUNNABLE 转为 BLOCKED
		  
		- 当原本的线程执行完毕时，会锁对象上所有的 BLOCKED 状态的线程进行竞争，竞争成功的由 BLOCKED 转为 RUNNABLE
	  
	- ## RUNNABLE 只能单向转换为 TERMINATED
	  
		- 当线程所有代码运行完毕，线程由 RUNNABLE 转为 TERMINATED


- # 多把锁
  
	- 当业务在存在不想关的业务时，可以将不同的业务使用不同的锁锁起来，这样可以提高并发度，但也容易出现死锁问题
	  
	- ## 死锁
	  
		- 举个简单的例子，线程A 已经获得了锁1，线程B 已经获得了锁2，这时线程A 想获得锁2，线程B想获得锁1，因为锁1 被线程A 占用，锁2 被线程B 占用，因此它们会一直阻塞直到有一方先释放锁，这就是死锁
		  
		- 可以通过顺序加锁的方式解决这个问题，即线程1，2 都是需要先获得锁1 再获得锁2，这样就不会出现死锁问题
	
	- ## 活锁
	  
		- 活锁是指两个线程互相改变对方的结束条件，最后导致谁也无法结束的情况，例如线程 t1 的结束条件为 count 的值为 0，每次循环会使 count - 1，线程 t2 的结束条件为 count 的值为 100，每次循环会使 count + 1，这样 t1 和 t2 会不断改变 count 的指，但谁也无法达到结束条件，这就是活锁
	
	- ## 线程饥饿
	  
		- 当一个线程由于优先级太低，始终无法被 cpu 调度执行，也不能结束的情况，就被称为线程饥饿


- # ReenterantLock 可重入锁
  
	- 相当于 synchronized 它具备如下特点：
	  
		- 可中断
		  
		- 可以设置超时时间
		  
		- 可以设置为公平锁
		  
		- 支持多个条件变量
	
	- ## 基本使用
	```java
		// 必须是静态的
		private static ReentrantLock lock = new ReentrantLock();
		
		lock.lock();
		try{
			// 临界区
		}
		finally {
			lock.unlock();
			// 释放锁放在 finally 中，即使临界区出现错误也能正确释放锁
		}
	```
	
	- ## 可重入
	  
		- 可重入是指同一个线程首次获得了这把锁，那么因为他是这把锁的所有者，可以再次获得这把锁，如果是不可重入锁，那么第二次获得锁时，自己也会被挡住
	
	- ## 可打断
	  
		- 如果想使用 reentrantLock 实现可打断效果，那么不能使用 lock 方法，而是使用 lockInterruptibly 方法加锁
		  
		- 实例
		```java
		Thread t1 = new Thread(() -> {
			try{
				lock.lockInterruptibly();
			}
			catch(e) {
				log.info(e)
				// 没有获得锁，结束
				return
			}
			try{
				// 获取到锁的代码
			}
			finally{
				lock.unlock
			}
		})
		
		// 主线程先获得锁
		lock.lock();
		// 启动 t1 线程
		t1.start();
		
		sleep(1);
		// 调用线程的 interrupt 方法打断等待，告知线程不要再等待获得锁了
		t1.interrupt();
		```
	
	- ## 锁超时
	  
		- 锁超时是指主动为获取锁加上一个期限，如果超过这个期限则认为获取锁失败，不再继续阻塞，可以防止死锁发生
		
		- 示例
		```java
		Thread t1 = new Thread(() -> {
			// tryLock 方法会返回一个布尔值标记是否成功获得锁
			// 参数可加可不加，不加就立即执行，加了就等待相应时间，到时还没有锁则结束
			// tryLock 也可以打断
			try{
				if (!lock.tryLock(1, TimeUnit.SECONDS)) {
					// 未获得锁
					return
				}
			}
			catch(e){
				e;
			}
			try{
				
			}
			finally{
				lock.unlock();
			}
		})
		```
	
	- ## 公平锁
	  
		- 公平锁是指锁会根据进入阻塞队列的顺序给予，而不是通过争抢的方式给予
		  
		- reentrantLock 默认是不公平的，可以在 new 锁时带参构造，示例：`ReentrantLock lock = new ReentrantLock(true);` 此时构建出来的锁就是公平锁
		  
		- 公平锁一般没有必要，会降低并发度
	
	- ## 条件变量
	  
		- 条件变量是指锁被线程获取时其余线程阻塞等待的地方，sychroniezd 只有一个等待的地方，之后称休息室，唤醒也是在所有线程中随机唤醒， ReentrantLock 有多个休息室，可以根据不同的条件唤醒不同休息室的线程
		
		- 示例
		```java
		// 创建休息室，可以创建多个
		Condition c1 = lock.newCondition();
		Condition c2 = lock.newCondition();
		
		lock.lock();
		
		// 进入休息室等待
		c1.await(Long n);
		
		// 唤醒休息室中的线程
		c1.signal()
		// 唤醒休息室中所有的线程 
		c.signalAll()
		```
	
	- await 前需要先获得锁
	  
	- await 执行后会释放锁，进入 ConditionObject 等待
	  
	- await 的线程被唤醒/打断/超时 后会重新竞争 lock 锁
	  
	- 竞争锁成功后从 await 后继续执行


- # 可见性
  
	- 线程中的内存分为主内存和工作内存，主内存是储存有各种变量信息的内存，工作内存是线程私有的内存，子线程在处理变量时需要将变量数据从主内存中读取到工作内存中
	  
	- 可见性为题是指，由于线程在循环中多次处理某一变量，为了效率起见，每一次不再是将数据从主内存读取到工作内存，而是直接将数据缓存在工作内存中，这时如果主线程对数据进行了修改，子线程中的数据仍然是修改之前的，子线程对主线程的修改不可见
	  
	- ## 解决方法
	  
		- 将需要修改的变量加上 volatile 关键字，该关键字会使其对应的变量不再被缓存至工作内存，必须去主内存中读取
		  
		- 将对变量的判断和修改部分放在 synchronized 锁中也可以解决
	
	- volatile 仅能保证可见性，不能保证原子性，适合用于一个写线程多个读线程的情况
