
- # 语法糖
  
	- 所谓语法糖，就是指 java 编译器把 java 源码编译为字节码的过程中，自动生成和转换的一些代码，主要是为了减轻程序员负担。
	
	- ## 默认构造器
	  
		- 如果在源码中没写任何构造方法，编译为字节码后也会自动的加上一个无参构造方法
	
	- ## 自动拆装箱
	  
		- 自动拆装箱是指自动在包装类和基本类之间相互转换，例如可以直接将一个 Integer 类型的变量赋值给 int。
	
	- ## 泛型
	  
		- java 中的泛型是指：例如在 spring 项目中的返回对象 R，源码中返回的是 `R<T>`这样的数据，其中的 T 就是泛型
		
		- JVM 中的泛型是指在编译时，编译器会将泛型信息抹除掉，替换为 Object，例如`List<String>` 在编译后会变成 `List<Object>` ，这一行为被称为类型擦除。
		  
		- 当从 `List<Object>` 中获取元素时，编译后的文件会执行类型转换 `Integer x = (Integer)list.get(0);`
		  
		- 引入泛型是为了：
			- **类型安全**：在编译时检查集合等容器中元素的类型，避免运行时 `ClassCastException`。
			  
			+ **消除强制转换**：减少代码中显式的类型转换
		
		- 类型擦除擦除的是字节码上的泛型信息，但是 LocalVariableTypeTable 中会保存有原本的泛型信息，使用反射仍然能获取这些信息
	
	- ## 可变参数
	  
		- 可变参数链接：[[11_集合进阶#可变参数]]
		  
		- 在编译时，编译器会根据传入的参数数量自动生成对应长度的数组，然后将参数放入数组中
		  
		- ![[可变参数.png]]
	
	- ## 数组赋初始值
	  
		- 可以像 `int [] array = {1,2,3}` 这样为数组赋初值，编译后代码为：`int [] array = new int[]{1,2,3}`
	
	- ## 增强 for 循环
	  
		- 编译时会自动将增强 for 循环改写为普通 for 循环
	  
	- ## switch 字符串
	  
		- switch 原本是不支持字符串和枚举类的，但在 jdk7 开始，通过语法糖支持了字符串和枚举类
		  
		- ### 字符串 switch
		```java
		// 源代码
		switch (str) {
			cache "hello" :{
				print("h");
				break;
			}
			cache "world":{
				print("w");
				break;
			}
		}
		
		// 编译后的代码
		btte x = -1;
		switch(str.hashCode()){
			case 99162332 : { // 99162332 是 hello 的hashCode
				if (str.equals("hello")) {
					x = 0;
				}
			}
			case 113318802 : { // 113318802 是 world 的 hashCode
				if (str.equals("world")) {
					x = 1;
				}
			}
		}
		
		switch (x) {
			case 0 :{
				print("h");
				break;
			}
			case 1 :{
				print("w");
				break;
			}
		}
		```
		
		- 可以看到，编译后执行了两边 switch，第一遍根据字符串的 hashCode 和 equals 将字符串转换为相应的 byte 类型。第二遍才用 byte 进行比较执行
		  
		- 第一遍即使用 hashCode 又使用 equals ，使用 hashCode 是为了提高效率，使用 equals 是为了防止哈希冲突
		  
		- ### 枚举 switch

		enum Sex{

		}
		
		// 源码

	- ## try-with-resources
	  
		- 使用`try(资源变量 = 创建资源对象) [] catch(){}` 可以不用写 finally 语句，编译器会帮忙加上 finally 部分的代码，关闭资源
	  
	- ## 方法重写时的桥接方法
	  
		- 方法重写时的返回值分两种情况：1.父子类的返回值完全一致。2.子类的返回值类型是父类的子类的一种
		  
		- 当情况为 2 时，编译器会重写一个方法，这个方法的返回值与父类相同，在这个方法中调用子类方法
	
	- ## 匿名内部类
	  
		- ### 没有引用局部变量的匿名内部类
		  
			- 这种匿名内部类在编译时会将匿名内部类摘出来，单独写成一个类，在原本的地方 new 这个类
		
		- ### 引用了局部变量的匿名内部类
		  
			- 这种匿名内部类会生成一个变量和一个构造方法，要求在 new 这个类时将引用的局部变量输入，其余与上相同


- # 类加载
  
	- ## 加载阶段
	  
		- 加载阶段是类加载的第一步，主要将类的字节码载入到方法区中，载入方法区中的数据使用 C++ 的instanceKlass 来描述 java 类。里面最重要的字段是 `_java_mirror`即 Java 的镜像类，作用是把 klass 暴露给 java 使用（虚拟机无法直接调用 c 中的方法），相当于 java 和 c 之间的桥梁
		  
		- 如果类的父类没有加载，会先加载父类。加载和后续的连接是交替运行的
		  
		- 图示：![[加载示例.png]]
	  
	- ## 验证阶段
	  
		- 主要验证类是否符合 JVM 规范，由四个阶段组成
		  
		  1. 文件格式验证（Class 文件格式检查）
		  2. 元数据验证（字节码语义检查）
		  3. 字节码验证（程序语义检查）
		  4. 符合引用验证（类的正确性检查）
	
	- ## 准备阶段
	  
		- 为 static 变量分配空间，设置默认值
		  
		- static 变量分配空间和赋值是两个步骤，分配空间在准备阶段完成，赋值在初始化阶段完成
		  
		- 如果 static 变量是 final 类型或是字符串常量，那么编译阶段值就确定了，赋值在准备阶段完成
		  
		- 如果 static 变量是 final 的，但属于引用类型，那么赋值也会在初始化阶段完成
	
	- ## 解析阶段
	  
		- 这个阶段将常量池中的符号解析为直接引用
	
	- ## 初始化阶段
	  
		- 初始化即调用类的 `<cinit>()V`，虚拟机会保证这个类的构造方法的线程安全
		  
		- ### 初始化的时机
		  
			- 类的初始化是懒惰的
			  
			- main 方法所在的类会被首先初始化
			  
			- 首次访问这个类的静态变量或静态方法时会进行初始化
			  
			- 子类初始化时如果父类没有初始化，会引起父类的初始化
			  
			- 子类访问父类的静态变量时，会引起父类的初始化
			  
			- 执行 `Class.forName` 时会触发初始化
			  
			- new 一个对象时会导致对象的类初始化
		  
		- ### 不会导致类的初始化的情况
		  
			- 访问类的 static final 静态常量（该常量为基本类型或字符串类型）不会导致类的初始化
			
			- 访问类对象的 `.class` 不会触发初始化
			  
			- 创建该类的数组不会触发初始化
			  
			- 使用类加载器的 `loadClass` 方法不会导致类初始化
			  
			- `Class.forName`  的第二个参数为 false 时不会导致初始化


- # 类加载器
  
	- 类加载器是一个负责加载类的对象，用于实现类加载过程中加载这一步。每个 java 类都有一个引用指向加载它的 `classLoader`。但数组类不是提高`classLoader`实现的，它是由 JVM 直接生成的
	  
	- 类加载器的主要作用就是动态加载 Java 类的字节码文件到 JVM 中，字节码可以是 Java 源程序
	  
	- JVM 启动的时候不会一次性加载所有类，而是根据需要动态进行加载，大部分类只有在使用时才会进行加载，已经加载的类会放在`classLoader`中，在类加载时，系统会先判断当前类是否被加载过，已经被加载的类会被直接返回，否则才尝试进行加载，也就是说，对于一个类加载来说，相同二进制名称的类之后加载一次 
	
	- 类加载器类型：![[类加载器类型.png]]
	
	- 从上到下分布是：启动类加载器，扩展类加载器和应用程序类加载器
	
	- 启动类加载器无法直接访问的原因是它是 c++ 代码写的，不是 java 代码，因此无法直接进行访问
	
	- 上面四个类加载器具有层级关系，在加载类时，会先问问上级是否加载过这个类 ，例如要加载字符串类，使用应用程序类加载器的 loadClass 方法加载 String 类，此时应用程序类加载器会先询问扩展类加载器是否加载了这个类，没有的话扩展类加载器向上询问启动类加载器有没有加载这个类，启动类加载器加载了这个类，那么扩展类和应用程序类加载器就不用管这个类的加载了
	
	- ## 启动类加载器
	  
		- 最顶层的加载类，由 C++ 实现，通常表示为 null，没有父级，主要用来加载 JDK 内部的核心类库
	  
	- ## 扩展类加载器
	  
		- 主要负责加载 `%JRE_HOME%/lib/ext` 目录下的 jar 包和类以及被 `java.ext.dirs` 系统变量所指定的路径下的所有类
	
	- ## 应用程序类加载器
	  
		- 面向用户的加载器，负责加载当前应用 classpath 下的所有 jar 包和类
	
	- ## 自定义类加载器
	
		- 除了启动器加载类其他类加载器均由 Java 实现并继承自 `java.lang.ClassLoader`，如果要自定义类加载器就需要继承`ClassLoader`抽象类
		  
		- `ClassLoader`类有两个关键方法：
		```java
		protected Class loadClass(String name, boolean resolve){}
		protected Class findClass(String name)
		```
		- loadClass 负责加载指定二进制名称的类，实现了双亲委派机制。name 为类的二进制名称，resolve 如果为 true 则在加载时调用 `resolveClass(Class<?> c)` 方法解析该类
		  
		- findClass 方法根据类的二进制名称来查找类，默认是空方法
		  
		- 如果不想打破双亲委派模型，就重写 `ClassLoader` 类中的 `findClass()` 方法即可，无法被父类加载器加载的类最终会通过这个方法被加载。但是，如果想打破双亲委派模型则需要重写 `loadClass()` 方法。


- # 双亲委派模型
  
	- ## 执行流程
	  
		- 在类加载的时候，系统会先判断当前类是否被加载过。已经被加载过的类会直接返回，否则才会尝试加载
		  
		- 类加载器在进行类加载的时候，它首先不会自己尝试加载这个类，而是把这个请求委托给父类加载器去完成，这样的话，所有的请求最后都会传到顶层的启动器加载类中
		  
		- 只有父加载器反馈自己无法完成这个加载请求（搜索范围内没有找到所需的类）时，子加载器才会尝试自己去加载，如果子加载器自己也无法加载这个类，就会抛出`ClassNotFoundException` 异常
	
	- ## 双亲委派模型的好处
	  
		- 避免类的重复加载和防止核心 API 被篡改
	  
	- ## 打破双亲委派模型的方法
	  
		- 写一个自定义加载器，重写 `ClassLoader` 的 loadClass 方法，因为默认的 loadClass 方法会按照双亲委派模型尝试让父类加载类，重写后可以自定义处理方式，比如在委派给父类之前，先自己尝试加载这个类或者在父类加载器返回后再尝试从其他地方加载这个类
