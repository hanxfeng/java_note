- # 单点 Redis 的问题

	- 数据丢失问题，宕机后数据消失，无法追回
	
	- 并发能力问题，单 Redis 服务器并发能力不弱，但在 618 这样的场景下仍然不足（我真的能到那种公司工作吗）
	  
	- 故障恢复问题，单 Redis 服务器，宕机后无法自动恢复
	  
	- 储存能力问题，单 Redis 服务器内存有限，因此能储存的数据也有限
  

- # RDB
  
	- RDB 全称 Redis Database Backup file （Redis数据备份文件），也叫做 Redis 数据快照，简单讲就是把内存中所有数据记录到磁盘，当 Redis 实例故障重启后，从磁盘读取文件，恢复数据
	  
	- 快照文件称为 RDB 文件，默认保存在当前运行目录
	  
	- 使用 `save` 命令进行备份，在保存过程中会阻塞所有命令
	  
	- `bgsave` 命令会开启一个子线程进行备份，避免主线程被影响
	  
	- 在正常停机时会自动进行备份
	  
	- 900 秒内至少有一个 key 被修改，则执行 `bgsave` 进行备份，300 秒内至少有十个 key 被修改，则进行备份，60 秒内有 10000 个 key 被修改则进行备份
	  
	- ## RDB 的底层原理
	  
		- 在 linux 中（因为 Redis 最开始只有 linux 端），应用不能直接操作物理内存中的数据，电脑会分配一份虚拟内存给应用，Redis 通过操作虚拟内存中的数据映射——页表来操作数据，`bgsave`  就是拷贝一份页表到子进程中，子进程根据页表将数据保存到磁盘中
		  
	- ## 缺点
		
		- RDB 执行时间长，两次 RDB 之间写入数据有丢失风险
		  
		- fork 子进程、压缩、写出 RDB 文件都比较耗时


- # AOF

	- AOF 全称 Append Only File （追加文件）。Redis 处理的每一个写命令都会记录在 AOF 文件，可以看做命令日志文件
	
	- AOF 默认是关闭的，需要修改 redis.conf 配置文件来开启 AOF
	
	- ![[AOF配置.png]]
	  
	- 由于是记录命令，AOF 文件会比 RDB 文件要大很多，而且对于同一个 key 的写操作，只有最后一次写操作才有意义，因此可以执行 bgrewriteaof 命令，让 AOF 文件执行重写功能，重写会精简文件，使用最少的命令达到与原来相同的效果。可以通过配置文件，使超过阈值时自动进行重写，有两种，一种是相比上次文件体积增大多少后重写，另一种是文件体积到达多大后重写，默认分别为 100 和 64mb


- # AOF 与 RDB 对比


|         | RDB                    | ADF                                |
| ------- | ---------------------- | ---------------------------------- |
| 持久化方式   | 定时对整个快照进行备份            | 记录每一次执行命令                          |
| 数据完整性   | 不完整，两次备份之间数据会丢失        | 相对完整，取决于刷盘策略                       |
| 文件大小    | 会有压缩，文件体积小             | 记录命令，文件体积大                         |
| 宕机恢复速度  | 很快                     | 慢                                  |
| 数据恢复优先级 | 低，因为数据完整性不如 ADF        | 高，数据更为完整                           |
| 系统资源占用  | 高，大量 CPU 和内存消耗         | 低，主要是磁盘 I/O 资源的，但重写时会占用大量CPU 和内存资源 |
| 使用场景    | 可以接受数分钟的数据丢失，追求更快的启动速度 | 对数据安全性要求高                          |


- # Redis 集群主从同步原理
  
	- ## 全量同步
	
		- 当从节点第一次向主节点申请同步数据时，会进行全量同步，即拷贝主节点中的所有数据
		
		- replid ：是数据集标记，主从节点进行全量同步后 replid 一致
		
		- offset ：偏移量，用于衡量从节点与主节点的数据差异程度，可以认为是 repl_baklog 的索引
		  
		- repl_baklog：保存命令的区域，可以认为是一个环形数组
		  
		- 同步过程：
		  
			1. 从节点请求增量同步
			  
			2. 主节点判断 replid，发现不一致，拒绝进行增量同步
			   
			3. 主节点将完整内存数据生成为 RDB，发送到从节点
			   
			4. 从节点清空本地数据，加载主节点的数据
			   
			5. 主节点将 RDB 期间的命令记录在 repl_baklog，将其中的命令发给从节点
			   
			6. 从节点接收到命令，与主节点保持一致
	
	- ## 增量同步
	  
		- 当从节点重启后，会自动进行增量同步
		
		- 根据从节点的 offset 主节点发送从节点 offset 之后的命令
		  
		- repl_baklog 大小有上限，写满后会覆盖掉原来的数据，如果从节点断开时间太久，导致未备份的数据被覆盖，那么就只能再次进行全量同步
	  
	- ## 主从集群优化
	
		- 在主节点的配置文件中配置 repl-diskless-sync yes 启用无磁盘复制，避免同步时的磁盘 I/O，多用于磁盘性能差但网络性能好时
		  
		- Redis 单节点上内存不要太大，减少 RDB 导致的过多磁盘 I/O
		  
		- 适当提升 repl_baklog 文件的大小，发现从节点宕机时尽快恢复，尽可能避免全量`同步
		  
		- 限制一个主节点上从节点的数量，如果从节点较多，可以使用 主-从-从 的链式结构，减轻主节点压力  
  

- # Redis 哨兵

	- ## 作用
	  
		- 监控：哨兵会不断监控主节点和从节点是否按照预期工作，哨兵一般由多个组成集群
		  
		- 自动故障恢复：如果主节点故障，哨兵会将一个从节点提升为主节点，当原来的主节点恢复后作为从节点不再恢复为主节点
		  
		- 通知：当集群发生故障转移时，会将最新信息推送给 Redis 客户端
	
	- ## 原理
	
		- ### 服务状态监控
		  
			- 哨兵基于心跳机制检测服务状态，每隔一秒向集群的每个实例发送 ping 命令，如果某个哨兵发现某示例未响应，则认为该实例主观下线，如果超过指定值的哨兵认为该实例主观下线，那么这个实例客观下线，这个值一般大于哨兵节点数量的一半
		
		- ### 选择新的主节点
		  
			- 首先判断从节点与主节点断开连接时间长短，如果超过指定值，就会直接排除该从节点
			  
			- 然后判断从节点的 slave-priority 值，越小优先级越高，0 则不参与选择
			  
			- 如果 slave-priority 相同，则判断从节点的 offset 值，越大说明数据越新，优先进行选择
			  
			- 最后判断从节点的运行 id 大小，越小优先级越高，因为 offset 相同，所以数据无差异，只是为了最终确定新的主节点制定的规则
			  
		- ### 实现故障转移（将从节点转为主节点）
		  
			- 哨兵会给选中的从节点发送 slaveof no one 命令，让该节点成为主节点
			  
			- 哨兵给其他从节点发生命令，告知主节点更改，从新的主节点上同步数据
			  
			- 最后将故障节点标记为从节点，当故障节点恢复后会自动成为主节点的从节点


- # Redis 分片集群

	- ## 特征
	  
		- 集群中有多个主节点，每个主节点保存不同数据
		  
		- 每个主节点都有多个从节点
		  
		- 主节点之间通过 ping 检测彼此健康关系
		  
		- 客户端可以访问任意集群节点，最终都会被转发到正确节点
	
	- ## 散列插槽
	
		- Redis 会把每个主节点映射到 0 - 16383 共 16384 个插槽上
		  
		- 在分片集群中，数据 key 不与节点绑定而是插槽绑定，redis 会根据 key 的有效部分计算插槽值，关于有效部分，分两种情况：
		  
			- key 中包含 {} 且 {} 中包括至少一个字符，{} 中就是有效部分
			
			- key 中不包含 {} ，整个 key 都是有效部分
		  
		- 将同一类数据保存在同一个节点中：
		  
			- 这一类数据使用相同的有效部分，在 key 中添加大括号且大括号内数据相同
	  
	- ## 集群伸缩
	  
		- 集群伸缩是为集群添加或删除一个节点，使用 add-node 命令添加
	  
	- ## 故障转移
	  
		- 当某一个主节点确认下线后，分片集群会自动将一个从节点提升为主节点
