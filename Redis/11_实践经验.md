- # 键值设计
  
	- ## key 设计
	  
		- Redis 的 key 可以自定义，但最好遵循下面的几个约定
		  
			- 遵循基本格式：`[业务名称]:[数据名]:[id]`
			  
			- 长度不超过 44 字节
			  
			- 不包含特殊字符
		
		- 其优点如下：
		  
			- 可读性强
			  
			- 避免key冲突
			
			- 方便管理
			  
			- 节省内存，key 是 string 类型，底层编码包括 int，embstr 和 raw 三种，embstr 在小于 44 字节时使用，采用连续内存空间，内存占用更小
	
	- ## 拒绝 BigKey
	  
		- BigKey 通常以 key 的大小和 key 中成员的数量来进行判断
		  
			- Key 本身数据过大，通常单个 Key 的大小大于 10Kb 就可以认为是 BigKey
			  
			- Key 的成员数过多，通常集合类型的 Key 成员数大于 1000 就可以认为是 BigKey
		  
		- ### 危害
		  
			- 网络阻塞：，对 BigKey 执行请求时，少量请求就可能导致带宽使用被占满，导致 Redis 实例甚至物理机变慢
			  
			- 数据倾斜：BigKey 所在 Redis 实例内存使用率远高于其他实例，无法使数据分片的内存资源达到均衡
			  
			- Redis 阻塞，对元素较多的 hash，list，zset 做运算会比较耗时，阻塞 Redis
			  
			- CPU 压力：对 BigKey 进行序列化反序列化时会导致 cpu 的使用率飙升，影响 Redis 实例和本机其他应用

- # 批处理优化
  
	- 对于执行一次 Redis 命令来说，耗时主要花在网络通信上，因此当处理大量数据时，会额外花费很多时间。
	  
	- ## Redis 原生解决方案
	
		-  因此可以使用 `mset` `hmset` 来批量插入数据，节省耗时，但要注意，不要在一次批处理中发送太多命令，否则单次命令占用带宽过多，会导致网络阻塞
	
	- ## Jedis 解决方案
	
		- Jedis 提供了 Pipeline 功能，用于一次性发送大量数据，示例如下：
		```java
		@Test
		public void testPipeline() {
			// 创建管道
			Pipeline pipeline = jedis.pipeline();
			
			for (int i = 1; i < 100000; i++) {
				// 放入命令到管道
				pipeline.set("test:key" + i, "value:" + i);
				if (i % 1000 == 0) {
					// 每放入一千条命令，批量执行一次
					pipeline.sync();
				}
			}
			
		}
		```
	
	- ## 集群下的批处理
	  
		- 如果使用 mset 或 pipeline 在集群中进行批处理，必须保证多个 key 必须落在同一个插槽，否则会导致执行失败，解决方式：![[集群批处理解决方式.png]]
		  
		- springBoot 中提供了 `.multiSet(Map)` 方法实现该功能，使用实例如下：
		```java
		@Test
		public void testMultiSet() {
			Map<String, String> map = new HashMap<>(3);
			map.put("name", "xiaoming");
			map.put("age", "21");
			map.put("sex", "F");
			redisTemplate.opsForValue().multiSet(map);
		}
		```


- # 服务端优化

	- ## 持久化配置
	  
		- 用来做缓存的 Redis 实例尽量不要开启持久化
		  
		- 更建议使用 AOF 持久化
		  
		- 使用脚本定期在从节点做 RDB 实现数据备份
		  
		- 设置合理的 rewrite 阈值，避免频繁 bgrewrite
		
		- 配置 no-appendfsync-on-rewrite = yes 禁止在 rewrite 期间 AOF，避免阻塞
		  
		- Redis 实例机要预留足够内存，应对 fork 和 rewrite
		  
		- 单个 Redis 实例的内存上限不要太大，例如 4g 或 8g。可以加快 fork 速度，减少主从，数据迁移压力
		  
		+ 不要与 cpu 密集型应用部署在一起
		  
		- 不要与高磁盘负载应用一起部署
	  
	- ## 慢查询
	  
		- 在 Redis 执行耗时超过某个阈值的命令叫做慢查询，不止是查询命令，其他命令也算
		  
		- 慢查询默认是 10 毫秒
		  
		- 慢查询会被放入慢查询日志中，该日志有上限为 128
		  
		- 慢查询部分是由于命令执行时间长导致的，这种原因导致的慢查询可以通过禁用引起慢查询的命令解决
		  
		- 还有一部分原因是数据结构不合理导致出现 BigKey 导致的，需要修改数据结构，消除 BigKey
	
	- ## 内存配置
	  
		-   当 Redis 内存不足时，可能导致 key 被频繁删除，响应时间变长，QPS 不稳定等问题，当内存占用率达到 90% 以上时，就需要检查内存占用的原因
		  
		- 可以使用 memory 系列命令来查看内存占用
		  
		- ### 数据内存
		  
			- 是 Redis 最主要的部分，储存 Redis 的键值信息。这部分的内存占用主要是 BigKey 问题，内存碎片问题（Redis 为数据分配内存时，会分配 $2^n$ 个字节，例如一个 10 字节的数据会分配 16 字节用于储存，多余 6 字节没有使用，多余的 6 字节就是内存碎片）
 		
		- ### 进程内存
		
			- Redis 主进程占用的内存，这部分内存占用越几兆，对内存影响几乎可以忽略
		
		- ### 缓冲区内存 
		
			- 一般包括客户端缓冲区，AOF缓冲区，复制缓冲区等，客户端缓冲区一般又包括输入缓冲区和输出缓冲区两种，这部分内存占用波动较大，不当使用 BigKey 可能会造成内存溢出
			  
				 - **复制缓冲区** ：主从复制的 repl_backlog_buf，如果太小可能会导致频繁的全量复制，影响性能，通过 repl_backlog_size 设置，默认 1mb
				   
				- **AOF 缓冲区** ：AOF 刷盘之前的缓存区域，AOF 执行 rewrite 的缓冲区，无容量上限，不过几乎不会导致内存占用过多的问题
				  
				- **客户端缓冲区** ：分输入缓冲区核输出缓冲区，输入缓冲区最大 1g 且不能设置，输出缓冲区可以设置。输入缓冲区是客户端给 Redis 的命令缓存的地方，输出缓冲区是 Redis 返回给客户端的数据缓存的地方。是
	
	- ## 集群问题
	
		- 在主从能满足需求的情况下，不建立集群
		
		- ### 集群完整性问题
		  
			- 在 Redis 默认配置中，如果发现任意一个插槽不可用，那么整个集群都会停止对外服务，建议将 cluster-require-full-coverage 设置为 false   
		
		- ### 集群带宽问题
		  
			- 集群节点之间会不断互相 ping 来确认彼此的状态，集群中节点越多，ping 携带的信息越大，每次集群互通需要的带宽会很大。
			  
			- 解决方法：
			  
				- 避免大集群，集群节点数在 1000 以内，多于这个节点则建立多个集群
				  
				- 避免在单个物理机运行太多 Redis 实例
				  
				- 配置合适的 cluster-node-timeout 值
